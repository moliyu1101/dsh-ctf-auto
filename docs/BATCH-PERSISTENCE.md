# 批量事务与任务维护保存

## 调整原因

任务协调端此前每题调用一次状态事务。一轮更新 20 道题的心跳，可能重复执行 20 次全库序列化、文件替换和 fsync，磁盘摘要检查也随题数重复。任务登记和派发等关键保存不能简单延迟，因此本轮先合并周期维护中的多题修改。

## 批量事务接口

`store.transactBatch(operations, {durable, includeSnapshots})` 接受至多 128 个不同题目的操作，每项包含 `id`、同步 `operation(edit, draft)` 和可选的 `expectedRevision`。它只覆盖现有题目的状态修改，不包含创建、删除、外部文件或网络操作。

```js
const result = store.transactBatch([
    { id: firstId, operation(edit) { edit.addEvent("note", "批量维护"); } },
    { id: secondId, operation(edit) { edit.addEvent("note", "批量维护"); } }
], { durable: true });
```

批量事务遵循这些规则：

- 在调用第一个操作前，取得全部原题目引用、内容修订和独立草稿。重复 id、缺少题目、非法参数和预期修订不匹配均拒绝整批。
- 全部操作完成同步校验后，才准备安装数据。回调抛错、返回 `{ok:false}`、返回 Promise、写入不可序列化数据或非法基础结构，均不安装任何草稿。
- 安装前再次核对原对象和内容修订，并检查全部待修改属性可安全替换。`state-snapshot.js` 预先复制待安装的数据属性，安装阶段不再调用业务回调或进行可能失败的结构化复制。
- 保留题目根对象及未变化字段的引用，避免破坏现有平台服务的任务身份判断。回调持有的草稿和返回结果也不会成为可变的内部存储对象。
- 有变化时，全批共享一次 `save()`，保留文件锁、磁盘摘要检查、原子替换及可选 fsync。无变化或空批次不保存；磁盘校验并未改成基于时间戳的猜测。
- 保存失败返回 `ok:false, applied:true, code:STATE_NOT_DURABLE`，内存保留整批一致修改并标记 dirty；恢复保存重试整份状态，不回滚其中一题或跳过耐久性要求。

结果包含每项的 `id`、`value`、`revision`、`applied`。默认不生成完整只读题目快照，避免后台维护再复制一遍大题目；显式设置 `includeSnapshots:true` 才返回逐题 `challenge`。准备或校验失败时不附带已准备的题目快照；保存失败但整批已经应用时返回逐项结果，宿主错误转换仍不向外暴露私有快照。

原 `transact()` 共用同一个事务实现，保留单题结果中的 value、revision、applied 和只读 challenge；内部调用方可用 `includeSnapshot:false` 关闭完整快照。任务流水的即时写入已使用这个选项。

## 回调与嵌套写入

回调只操作传入的草稿，不执行 I/O。准备阶段调用 `save()`、`close()`、另一个事务或旧写接口，会触发 `TRANSACTION_REENTRANT`。即使回调捕获错误或忽略嵌套事务的失败结果，外层仍拒绝整批，不在中途写入另一份状态。

这些保护不是执行沙箱：无法撤销回调自行进行的文件、网络操作或通过旧 `state/get/list` 可变引用造成的非法改动。旧可变接口仍需后续收敛；单题内容修订仍有 ABA 等既有边界。

## 任务维护如何合并

`task-registry.tick()` 先收集维护计划，再按题目合并：每轮最多选 20 道需要心跳、恢复或迁移的题目，另取最多 20 条待补存的完成计划。同题的多个计划进入同一草稿，正常最多涉及 40 道题，只调用一次批量保存。没有到期心跳或恢复工作时不保存。

启动恢复仍先处理全部已有记录；每个批次至多 128 道题，不把大批迁移装入一个无限制的草稿集合。跨批次不宣称整体原子性：先前批次可以已经保存，失败批次整批保留待恢复，后续批次停止处理。未迁移记录和未知任务继续阻止调度。

心跳和关联任务的修改只在草稿中进行，不提前更新运行时租约字段。保存成功后才清理待补存完成计划、通知已安全结束的任务及恢复候选自动提交。写入失败且修改已应用到内存时，过期任务仍可收到尽力取消通知，但不会把未持久化的完成状态作为成功通知出去。

运行时续租现在以单调时钟计时，并在整批保存返回时检查旧截止时间：写盘期间已过期的任务不接受本批续租，即使文件里已经安装了新的审计时间。先完成同批运行时进度处理，再发送可能触发其他保存的取消通知；墙上时间字段不直接授予执行权限。

任务登记、派发、平台发送边界、用户取消和即时完成记录仍立即保存；它们不等待下一轮心跳。恢复通知可能进一步触发停止事务，因此“维护保存合并为一次”不等于整个看门狗周期只能有一次状态写入。20 道普通心跳的 20 次维护保存合为 1 次，是调用结构变化，不是实测吞吐量结论。

## 诊断

`state.get.persistence.io` 和诊断入口返回本实例的计数：

| 字段 | 含义 |
| --- | --- |
| `reads` / `readBytes` | 状态文件读取次数及读入文本的 UTF-8 字节量 |
| `saveAttempts` | save 调用次数，包含失败 |
| `writes` / `writeBytes` | 已安装到状态路径的文件次数和内容字节量，后续目录同步失败仍计入 |
| `lastSaveMs` / `totalSaveMs` | 最近及累计 save 耗时，使用单调时钟，不含前面的草稿准备时间 |
| `transactionCommits` / `transactionChallenges` | 事务直接保存成功次数及其中实际改变的题目数量，包含单题事务 |
| `multiChallengeCommits` | 一次直接保存成功、实际改变多道题的次数 |

`state.get.taskStorage` 返回活动任务数、待补存完成数及 `lastTick`。最近一轮包含选中题数、保存批次数、改变题数、续租数量、恢复数量、完成计划数及错误。诊断工具 `ctf_solve_doctor` 与 Web doctor 同样提供这些数据，题板展示任务维护错误。

计数不落盘，重启清零；它们是应用层文本 I/O 与调用计数，不是操作系统实际物理读写量或压测结果。读取诊断本身可能执行既有的磁盘状态检查。

## 当前边界

批量事务没有引入 SQLite、追加式日志、增量文件格式或独立读模型。每次实际保存仍序列化和写入整份 JSON，题目修订、复制和摘要校验仍有成本。状态格式现为 v3，继续读取 v1/v2；新增题面文件待办的降级保护见 [平台刷新](PLATFORM-REFRESH.md)。

事务只覆盖同一状态文件，同步执行并受单写者锁保护，不提供跨文件或跨独立状态目录事务，也不替代远端任务停止确认。

按当前范围未新增或运行测试、未修改 CI，沙箱继续暂缓；仅通过语法和差异检查，真实宿主及负载行为尚未运行验证。
